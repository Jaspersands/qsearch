How it works

Most proposals for new quantum algorithms fall apart for one of two reasons: a classical algorithm turns out to do the same job, or the idea only works on small examples. Q-Search is set up to find out which, as early as possible, and to write the answer down.

The loop

Every idea goes through the same four steps.

  1. Propose

    Write down a candidate quantum procedure for one specific problem, including the exact measurement it would make.

  2. Attack classically

    Try to get the same answer with classical methods: information-set decoding, lattice reduction, Weisfeiler–Leman refinement, Fourier methods. If one works, the quantum idea offers no speedup.

  3. Record

    Every idea that fails goes into the negative-results registry with the reason and the lesson, so it isn't tried again.

  4. Proof gate

    An idea that survives still can't be called a speedup until its missing proofs, its proof debts, are written and checked.

Ideas that survive the gate at small sizes go back to step 2 at larger sizes. So far, none has made it through.

Terms used on this site

Hidden subgroup problem
A family of problems where a function hides a subgroup and you have to find it. Shor's factoring algorithm solves the abelian case. The dihedral and symmetric-group cases are open.
Code equivalence
Deciding whether two error-correcting codes are the same up to reordering their coordinates. Some post-quantum cryptography depends on this being hard.
Dequantization
Showing that a classical algorithm can do what a proposed quantum one does, about as fast. A dequantized idea offers no speedup.
Negative result
A recorded failure: the claim that was tested, why it's false or blocked, and what to do differently next time.
Proof debt
A proof that has to exist before a claim can be made. For example, that a reduction really preserves the original problem, or that no known classical method already works.
Kill criterion
A condition, decided in advance, that ends a line of research if it's met.

What's in the repository

Everything on this site is generated from these folders.

PathWhat it holds
qsearch.pyThe command-line entry point for every registered workflow.
core/The framework: research registry, experiment runner, proof gate, and the classical-attack scanner.
theorems/One module per verification workbench: dihedral and phase-state problems (dcp_*), coset states (coset_*, cfi_*), wreath products (self_dual_wreath_*), and code equivalence (code_*, goppa_*, bch_*).
research/registry/The canonical registries: candidates, experiments, results, negative results, and dequantization checks.
research/Generated outputs for each area, the written derivations (*.md), the frontier map, and the proof-debt report.
tests/Unit, integration, and registry tests.
tools/Scripts that build and check this website's data.
site/This website's styles, scripts, and data files.

Main commands

Run these from the repository root.

python qsearch.py validate
python qsearch.py run-next
python tools/build_progress_snapshot.py
python tools/build_site_data.py
python -m pytest tests/

validate checks every candidate and experiment against its proof obligations. GitHub Actions runs it on every push.

run-next runs the highest-priority registered experiment.

The two build scripts regenerate the files this website reads.

Limits

  • Numerical checks are not formal proofs. Many derivations in the registry are marked review-pending: written down and checked by scripts, but not yet independently reviewed.
  • Results at small sizes don't establish how an idea scales. The proof gate exists because small cases often look better than large ones.
  • Research runs in interactive sessions directed by Jasper Sands, using AI coding agents. GitHub Actions validates every push. Nothing runs on its own between sessions.
  • No speedup is claimed. The site will only say otherwise once every proof debt for that claim is closed.
